## 🔴 Критические проблемы производительности

### 1. **Polling без оптимизации** (КРИТИЧНО)

**Проблема:**
```typescript
// App.tsx:667
const pollInterval = setInterval(async () => {
    const order = await fetchOrder(currentInvId);
    // ... обновление состояния каждые 2 секунды
}, 2000);
```

**Проблемы:**
- ❌ Polling продолжается даже после завершения заказа (останавливается только при `completed`/`failed`)
- ❌ Нет exponential backoff при длительном ожидании
- ❌ Нет отмены запросов при размонтировании компонента
- ❌ Каждый polling-запрос вызывает полное обновление состояния → лишние ререндеры

**Рекомендации:**
1. ✅ Использовать WebSocket или Server-Sent Events вместо polling
2. ✅ Добавить exponential backoff (2s → 4s → 8s → 16s, макс 30s)
3. ✅ Останавливать polling сразу после `completed`/`failed`
4. ✅ Использовать `AbortController` для отмены запросов
5. ✅ Мемоизировать `fetchOrder` результат, если данные не изменились

**Приоритет:** 🔴 КРИТИЧНО

---

### 2. **Избыточное логирование в продакшене** (ВЫСОКИЙ)

**Проблема:**
- 91 `console.log` в App.tsx
- 45 `console.log` в server/index.js
- Логирование каждого HTTP-запроса на бэкенде

**Проблемы:**
- ❌ Замедляет работу в браузере (особенно на мобильных)
- ❌ Увеличивает размер бандла
- ❌ Потенциальная утечка данных в консоль

**Рекомендации:**
1. ✅ Использовать условное логирование: `if (process.env.NODE_ENV === 'development')`
2. ✅ Заменить `console.log` на библиотеку логирования (например, `pino` для бэкенда)
3. ✅ Удалить логи из критичных путей (polling, рендеринг)
4. ✅ Оставить только error/warn логи в продакшене

**Приоритет:** 🟡 ВЫСОКИЙ

---

### 3. **Монолитный App.tsx** (ВЫСОКИЙ)

**Проблема:**
- 2448 строк в одном файле
- 32 `useState` хука
- Смешанная логика: UI, бизнес-логика, обработка изображений

**Проблемы:**
- ❌ Сложно поддерживать и тестировать
- ❌ Лишние ререндеры из-за большого количества состояний
- ❌ Нет возможности code-splitting

**Рекомендации:**
1. ✅ Разбить на компоненты:
   - `ImageUploadFlow` (загрузка + валидация)
   - `GenerationFlow` (генерация + polling)
   - `ResultsView` (отображение результатов)
   - `OrderManagement` (управление заказами)
2. ✅ Вынести бизнес-логику в кастомные хуки:
   - `useOrderPolling`
   - `useImageValidation`
   - `useGeneration`
3. ✅ Использовать Context API для глобального состояния (order, images)
4. ✅ React.memo для тяжелых компонентов

**Приоритет:** 🟡 ВЫСОКИЙ

### 4. **Хранение больших изображений в localStorage** (СРЕДНИЙ)

**Проблема:**
```typescript
// App.tsx:1014
window.localStorage.setItem(PENDING_GENERATION_KEY, JSON.stringify({
    uploadedImage, // base64 строка может быть 2-5MB
    // ...
}));
```

**Проблемы:**
- ❌ localStorage ограничен ~5-10MB
- ❌ Синхронная операция блокирует UI
- ❌ Неэффективно для больших изображений

**Рекомендации:**
1. ✅ Использовать IndexedDB для больших данных
2. ✅ Или хранить только метаданные (размер, тип), а изображение загружать заново
3. ✅ Использовать `sessionStorage` вместо `localStorage` для временных данных

**Приоритет:** 🟢 СРЕДНИЙ

---

### 5. **Отсутствие мемоизации компонентов** (СРЕДНИЙ)

**Проблема:**
- `ImageCard` рендерится при каждом изменении родительского состояния
- Нет `React.memo` для тяжелых компонентов
- Нет `useMemo` для вычисляемых значений

**Рекомендации:**
1. ✅ Обернуть `ImageCard` в `React.memo`
2. ✅ Использовать `useMemo` для фильтрации/сортировки списков
3. ✅ Использовать `useCallback` для колбэков, передаваемых в дочерние компоненты

**Приоритет:** 🟢 СРЕДНИЙ

---

### 6. **Дублирование запросов к бэкенду** (СРЕДНИЙ)

**Проблема:**
- `fetchOrder` вызывается и в `useEffect` загрузки, и в polling
- Нет кэширования результатов запросов
- Возможны race conditions при параллельных запросах

**Рекомендации:**
1. ✅ Использовать библиотеку для кэширования (React Query, SWR)
2. ✅ Или реализовать простой кэш с TTL
3. ✅ Дедуплицировать запросы с одинаковыми параметрами

**Приоритет:** 🟢 СРЕДНИЙ

**Рекомендации:**
